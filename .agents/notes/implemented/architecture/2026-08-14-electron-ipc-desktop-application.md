# Agent Note: Electron IPC desktop application with a zero-port utility Host

Status: implemented

English | [中文](2026-08-14-electron-ipc-desktop-application.zh.md)

## Problem

The GUI was deployable only as a browser application. Its shared Client packages and channel-independent RPC protocol already reserved an Electron carrier, but the shipped composition still coupled the complete GUI roster to Web startup, HTTP/WebSocket serving, browser trust configuration, and Web-only module delivery. Reusing that composition inside Electron would either open an unnecessary loopback port or keep a disabled Web dependency closure whose lifecycle and security obligations the desktop application did not need.

Electron also creates a different trust and process model. The renderer must not inherit Node.js authority or a generic `ipcRenderer`; the Harness Host must remain capable of loading Node plugins and native providers; streaming responses must not let a fast Host overwhelm the renderer through structured clone; and packaged resource lookup cannot rely on `file://` paths or a development checkout layout. A desktop shell therefore needs one explicit owner for renderer resources, Host lifecycle, IPC request ownership, and future packaging.

## Decision

The desktop product is `apps/electron` (`@deepseek-ai/dsh-desktop`). It implements the Electron reservation in the [GUI layering and RPC protocol decision](2026-07-19-gui-layering-and-rpc-protocol.md) without introducing a second application protocol. The application has three independently built entry points: an ESM main process, an ESM utility Host, and a CommonJS preload. The renderer continues to run the built `dsh-web-frontend` shell and the ordinary Client plugin graph.

### GUI composition and renderer resources

GUI composition has three ordered layers. `@deepseek-ai/dsh-base` owns the core process rows; `@deepseek-ai/dsh-gui-app` owns transport-independent Host services, API and module inventory, Agent Presets, and the shared Client/UI roster; exactly one surface follows it. `@deepseek-ai/dsh-web-app` owns Web startup, `webServer`, Web runtime glue, client HMR, browser connection trust, and adaptive directory interaction. `@deepseek-ai/dsh-electron-app` instead pins the existing native Host directory picker and its Client interaction, and contains none of those Web rows. This extends the [profile bundle decision](2026-08-05-profile-plugin-bundles.md): shipped Web profiles compose `base + gui-app + web-app`, while desktop composes `base + gui-app + electron-app`.

The `dsh-client-modules` Host face is an inventory independent of any carrier. It always scans the mounted Loader tree, composes the boot graph, exposes each graph entry's built bundle path, and publishes graph-change notifications. Its Web route and index-manifest adapter mount only when `webServer` exists. The desktop utility Host reads the same graph and paths, then sends an opaque graph plus a pathname-to-absolute-path resource list to the main process. This keeps the [client plugin loading model](2026-07-23-client-plugin-loading-model.md) unchanged in the renderer: plugin ids, revisions, dependency edges, factories, and Loader lifecycle are identical across Web and Electron.

The main process registers `dsh` as a standard, secure scheme during ESM evaluation, then schedules the remaining startup work after Electron readiness without suspending entry-module evaluation. It serves exactly one application origin, `dsh://app`. The scheme handler injects the Host-authored boot graph under a per-response nonce admitted by the same response's CSP, serves Vite's root-relative assets from the resolved frontend dist, and serves `/plugins/...` only from the current Host inventory. A standard origin lets the existing absolute asset and plugin URLs resolve normally and gives CSP, same-origin checks, Fetch URL parsing, and code caching coherent semantics that `file://` does not provide.

The strict desktop CSP omits `unsafe-eval`. The vendored Loader therefore keeps its JavaScript-expression evaluator uninitialized until a Loader expression is interpolated: importing Loader for static Client entry governance creates no `Function`, while the Node utility Host may initialize the evaluator when Host configuration uses `!!js`. This permits the ordinary static Client graph to boot without weakening the renderer policy.

The same CSP path runs a nonce-authorized bootstrap before the boot manifest and every Client bundle, setting `globalThis.__zod_globalConfig.jitless = true`. Zod observes that value when imported, skips its `new Function` capability probe and JIT object-parser path, and performs ordinary schema validation through its jitless parser without producing a CSP violation.

### Process and security model

The main process is the only broker between the renderer and the utility Host. The `BrowserWindow` disables Node integration, enables context isolation, sandboxing, Web security, and a restrictive Content Security Policy, denies permission checks and requests, rejects webviews, blocks application-window navigation outside `dsh://app`, and opens only HTTP(S) links through the operating system. Every IPC invocation must come from the one owned window and a `dsh://app` sender frame.

The preload exposes one fixed `window.__DSH_DESKTOP__` object: serialized `fetch`, one-chunk `pull`, idempotent `cancel`, native `saveDownload`, and immutable desktop metadata. It does not expose Electron objects, arbitrary channel names, filesystem access, process access, or a selected path. The main process validates request ids, the exact application origin, admitted methods, header fields, and the shared `DEFAULT_MAX_REQUEST_BODY_BYTES` ceiling before forwarding a request; native save additionally admits only the Session export URL and a safe suggested filename before opening the OS dialog. The utility Host validates each command again. Client Connection validates response heads and chunks before reconstructing browser objects.

Settings schema rehydration follows the same renderer rule. Serialized callback source becomes an identity transform, so Client editors retain structural validation without executing callback code; every write still passes through the authoritative Host schema, including its real callbacks.

Runtime-installed Client halves are the deliberate exception to static Client loading. `cordis-client-runner` currently evaluates their source strings with `new Function`, which the desktop CSP forbids. The shipped static Client graph continues to run, and runtime-installed Host halves still execute in the utility Host. Supporting dynamic Client code requires a delivery or evaluation mechanism without string code generation rather than adding `unsafe-eval`.

The utility process is a trusted Node Host, not an OS security sandbox. It boots the ordinary desktop profile through `bootProfile`, provides the launch environment, loads user-selected Host plugins with their normal authority, and owns the Cordis application fiber. Desktop uses the vendored HMR service with `root: []`: exact profile and home patch watches stay active without reading Loader's internal module loader, while module HMR stays disabled. The packaged utility process therefore needs no `--expose-internals` exception. The renderer sandbox and narrow preload limit a compromised renderer's Electron authority, but they do not make Client plugins mutually untrusted and do not confine a Host plugin that the user chose to install.

Desktop requests bypass the Web Host/Origin trust fence only after the main-process sender check. `HostConnectionHandle.fetch(Request)` is explicitly local-carrier trusted; it dispatches registered logical channels, then a shared `/api` interceptor, then the API Proxy fallback. The optional Web adapter still applies browser authority policy before calling the same dispatcher. Thus desktop does not pretend to be a loopback browser and does not weaken the [browser trust decision](2026-07-28-api-browser-trust-boundary.md) for real HTTP/WebSocket traffic.

### Pull-based Fetch and SSE over IPC

The Client Connection plugin selects the fixture when requested, otherwise the exact desktop preload global when present, and otherwise the Web carrier. Desktop selection creates one `createDesktopFetch` function shared by `DesktopApiClient` and generic Connection RPC. `DesktopApiClient` changes only `AbstractApiClient.doFetch`; request envelopes, response schemas, correlation, transport-error handling, and the two logical event streams remain the same protocol.

A desktop fetch serializes the URL, method, headers, and bounded body under one renderer-minted opaque id. The utility Host rebuilds a local `Request` and calls `ctx.connection.fetch` directly, so neither unary RPC nor streaming opens a socket. It returns response metadata first and retains the response body's reader. The reconstructed renderer `ReadableStream` issues exactly one `pull(id)` for each demand signal; the utility performs exactly one reader read and returns one chunk, end, or error. The existing SSE decoder therefore carries `events.mux` and `events.host` over IPC with renderer-driven backpressure, while the Web carrier continues to use HTTP uplink and WebSocket downlinks as recorded in the [WebSocket carrier decision](2026-08-04-websocket-downlink-carrier.md).

The desktop IPC adapter imports `DEFAULT_MAX_REQUEST_BODY_BYTES` from Client Connection and currently enforces the same 160 MiB ceiling as the Web bridge. That ceiling covers the default 100 MiB aggregate image allowance after base64 expansion plus envelope headroom and prevents carrier-specific capacity drift. Both carriers still buffer each complete request body, and Electron additionally transfers it as one structured-clone value; reducing that resident-memory cost requires a streaming request path or smaller configured image limits.

Session export does not send ZIP chunks through the renderer. The main process obtains the destination from Electron's save dialog and sends that approved absolute path to the utility Host. The Host uses the same local Connection dispatcher, writes one response chunk at a time to a mode-0600 sibling temporary file, and renames it into place only after the stream succeeds. Cancellation and stream failures remove partial files, while the selected path remains absent from Client code.

An `AbortSignal`, a renderer stream cancellation, window teardown, and app shutdown converge on the same request id. Cancellation removes remote ownership, aborts the utility-side `Request`, cancels a retained body reader, and settles duplicate cancellation safely. The main process rejects duplicate ids, concurrent pulls, and a renderer trying to consume another renderer's response. This per-request ledger is also the ownership point for failing all outstanding callers if the utility Host exits.

### Application lifecycle

The main process holds a single-instance lock, installs the scheme and IPC handlers, starts the utility Host, and waits for its ready graph before creating and showing the window. The utility publishes later graph changes to the main process, which atomically replaces the scheme resource map. A Host fatal error rejects pending IPC and replaces the application view with a failure diagnostic instead of leaving a connected-looking shell.

Every profile Host, including Web and Electron, acquires `$DSH_HOME/.host.lock` through `bootProfile` before mounting its Cordis tree. The lock is one deferred `withFileLock` operation whose lifetime ends only through the returned idempotent `dispose()`: disposal first waits for the application fiber to reach quiescence, then releases the lock. Startup failure follows the same release path. This process-wide ownership prevents the JSONL Session and JSON Storage backends from writing one Harness home concurrently.

Normal quit first marks the utility Host as stopping, so new fetch, save, and pull commands are rejected while cancellation remains available. Shutdown cancels every active request, drains all in-flight fetch, save, pull, and cancel handlers, disposes profile boot and releases the Home lock, posts the `stopped` acknowledgment, then exits naturally on the next event-loop turn. The main process gives acknowledgment and natural exit one shared two-second graceful deadline. If an acknowledged Host does not exit by that deadline, main kills it and waits an independent two seconds for termination. A Host that reaches the deadline without acknowledgment is killed and makes the application fail even when forced termination succeeds; any non-zero exit before forced termination fails, and failure to exit after the kill also fails. Quit before readiness, startup fatal events, and runtime Host failure converge on one single-flight application-stop owner, which preserves the highest requested exit code and calls `app.exit` only after Host shutdown settles. Closing the sole window cancels its pending requests. The application intentionally supports one window, so sender identity and request ownership do not require a cross-window routing policy.

### Packaging status

`apps/electron/package.json` is both the application manifest and the desktop deploy root. Its production dependencies supply every required workspace peer reachable from the desktop composition; the conditionally injected theme integration marks WebServer as optional, so this closure does not reintroduce the Web carrier. `pnpm package:mac` checks that graph, builds the Host and Client artifacts, and uses the frozen lockfile to inject production workspace packages into an isolated hoisted staging tree without dependency lifecycle scripts. It resolves each dependency and required peer from the owning staged package, imports the external main and Host roots with plain Node, validates the frontend dist, desktop entries, shipped Agent Presets, Client bundles, workers, native code, libvips, `rg`, `spawn-helper`, and every remaining symbolic link, and rejects a deploy that changes repository installation metadata.

`@electron/packager` copies the validated staging root with `asar: false` and dereferences its contained links. The desktop install anchor, profile patches, dynamic bundle paths, native code, and helper executables therefore remain ordinary relocatable filesystem resources without retaining staging paths. The copied application repeats the production-entry import and link checks before signature verification. The default product receives an ad-hoc signature for local use; a configured Developer ID identity and one complete credential strategy enable hardened-runtime signing and notarization in the same command.

The Host also launches Node helpers through `process.execPath`. The current Windows ACL sandbox, persistent terminal, and native directory-picker paths apply `ELECTRON_RUN_AS_NODE=1` only to the outer JavaScript helper; the ACL runner removes it before starting the caller's command. The package retains Electron's RunAsNode fuse while these helpers use the Electron executable. Each macOS architecture builds on a matching host because pnpm selects architecture-specific native dependencies during staging. Universal applications, DMG generation, product icons, Windows signing and installers, and update delivery remain explicit release work.

## Verification

Bundle composition tests apply patches over an empty root and pin both supported chains: desktop retains the shared modules, Connection, API, UI, and Agent Preset rows while containing no `web-startup`, `webserver`, `web-runtime`, or `client-hmr`; Web retains the same shared roster and adds its carrier rows and connection configuration. The same tests require every bare plugin in each patch to appear in that bundle's manifest.

Connection tests exercise desktop bridge detection, Fetch reconstruction, one-pull-per-chunk backpressure, SSE consumption through `DesktopApiClient`, abort and stream cancellation convergence, non-OK body cleanup, response validation, and shared generic RPC transport. Application tests prove main-entry ESM evaluation completes while readiness is pending, cover the response-header CSP and the nonce-bound ordering of Zod jitless configuration, boot manifest, and shell bundle, native save replacement and partial-file cleanup, installed CLI preset resolution, and protocol rejection of foreign origins, disallowed methods, oversized request bodies, malformed ids, and invalid utility commands. Vendored HMR tests prove an empty module-root list supports exact config watching without Loader internals and a non-empty list fails loud without them; app-boot tests cover the profile and home patch registrations. A clean-process smoke opens the initial plugin graph and Settings → Models under the strict policy; DevTools reports “No Issues” and zero console messages. Profile-runner tests hold the Home lock across boot, reject a concurrent same-Home Host, admit sequential reuse, coalesce repeated disposal, and prove startup failure releases the lock. Sandbox and terminal tests cover the Electron-only outer-runner environment without forwarding it to user commands. Packaging tests pin modern injected hoisted deploy arguments, artifact containment, signing modes, credential completeness, external staging-link rejection, staged dependency-resolution failure, and production-entry import failure; the real packaging command additionally verifies its frozen deployed closure, unchanged repository installation metadata, property list, code signature, and ZIP. `pnpm desktop` and `pnpm package:mac` both rebuild the libraries and Web shell before consuming them unless packaging explicitly receives `--skip-build`.

## Alternatives considered

**Compose `web-app` and disable its rows in a desktop overlay.** Rejected because Loader state would look correct while the desktop package still depended on Web startup, server, frontend-serving, HMR, and adaptive-picker packages. The shared `gui-app` layer gives each surface a clean dependency closure and makes accidental Web reintroduction visible in composition tests.

**Run the existing Web application on a loopback port inside Electron.** Rejected because it adds port collision, firewall, DNS-rebinding, browser authority, server shutdown, and URL-discovery concerns to a local application. Zero-port IPC reuses the protocol without reusing a physical carrier whose risks do not apply.

**Run the Harness Host in Electron's main process.** Rejected because plugin activation, CPU work, and teardown would share the process that owns windows, navigation policy, protocol serving, and IPC request ledgers. A utility process gives the trusted Host an independent event loop and a bounded kill fallback without claiming it is a hostile-code sandbox.

**Expose `ipcRenderer` or a generic invoke bridge.** Rejected because channel names and Electron values would become renderer-controlled application API. The fixed Fetch-shaped bridge is the minimum authority the existing Client protocol needs and leaves channel routing in the main process.

**Push response chunks and Host events over IPC.** Rejected because push ignores renderer demand and would require a second buffering and flow-control protocol. Pulling one chunk per `ReadableStream` demand preserves Fetch backpressure and lets the existing SSE decoder remain the only event framing implementation for non-Web carriers.

**Load the shell from `file://`.** Rejected because it gives root-relative Vite assets and plugin URLs no stable application origin, complicates CSP and same-origin behavior, and couples renderer URL semantics to filesystem layout. The private standard secure scheme names application resources without granting arbitrary file reads.

**Rely on Electron's single-instance lock for Harness-home ownership.** Rejected because it cannot see a Web or headless Host using the same Home. The shared profile boot point owns one cross-platform exclusive-create lock for every Host carrier instead of duplicating persistence-specific locks across Session and Storage backends.

## Consequences

Electron reuses the same API definitions, Client bundles, module graph, Agent Presets, settings, credentials, sessions, and workspaces as Web without opening a network listener. Web-specific serving and trust policy remain owned by the Web surface, while transport-neutral Host inventory and Connection dispatch are reusable application infrastructure.

The shared Harness home is a single-Host resource. Web, CLI, and Electron processes may reuse it sequentially; a concurrent profile boot times out on `.host.lock` and fails before mounting plugins. Intentional concurrency requires distinct `$DSH_HOME` roots. An unclean exit can leave the lock file behind, and recovery is deliberately manual: an operator confirms no Host still uses the Home before removing it. Neither file age nor a PID guess authorizes automatic lock stealing.

The cost is a real broker protocol and three-process lifecycle: request ids, body readers, cancellation, graph resources, fatal errors, and shutdown all require explicit ownership. The single-window restriction keeps that state small today. Source execution and product packaging remain separate evidence: `pnpm desktop` proves the workspace application, while `pnpm package:mac` proves one native-architecture, signed, relocatable product closure.
